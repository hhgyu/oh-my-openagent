## 2026-11-12 - Fresh-device memory sync starts in the first Senpi session (#30)

Follow-up to #29 (parity P-22). memory-core `sync/runner/sync-runner.ts` kept a failed start held: on a fresh device the bind ran space resolution on a repository that did not exist yet, `launch` logged `memory sync failed to start` and resolved `null`, and later acquires of the same repo only raised the refcount, so sync stayed off until every session released the repo. The runner now checks the repo (`.git` exists, injectable `repoSeeded`) before resolving a session; an unseeded repo logs `sync waiting: the memory repository does not exist yet` once and is held as `unseeded`. A new `SyncRunner.resume(repo)` starts that held repo again once the repository exists, without touching the refcount, and is a no-op for every other state, so a start that keeps failing is never retried per turn. `acquire` on a held repo whose start settled as `unseeded` or `failed` starts it again with the refcount carried over: a new session is the retry edge. The Senpi memory component calls `resume` for the settling session's repo on `agent_settled`. The OpenCode 2 host is unchanged: it already waits for the repository before acquiring. Parity row P-22 updated. Live Senpi QA (`scripts/qa/memory-sync-fresh-device-e2e.mjs`, signed-out device with a dead loopback service origin) shows the waiting line at bind and a second start attempt after the first write's settle on this build, and no second attempt on the base build. A signed-in engine opening after the seed is pinned by unit tests only. References: https://github.com/hhgyu/oh-my-openagent/pull/30.
