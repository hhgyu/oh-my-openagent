### Added

- OpenCode 2 root sessions can get the Native `eval` tool again (on by default like Native; the plugin option `omo-native-eval-enabled: false` turns it off): persistent JavaScript and Python kernels, QuickJS sandbox cells with `isolate: true`, and abort per call. The runtime starts in a background worker on the first call (a few seconds, without freezing OpenCode), each session gets its own kernels, and they are shut down when the session is deleted, the plugin unloads or the process exits. Read-only agents and child sessions do not get it, and your `eval` permission rules apply. Set `omo-native-eval-sandbox` to `false` to drop sandbox cells.

## 2026-11-12 - OpenCode 2 Native eval over senpi-codemode (#25)

S9c of the OpenCode 2 CodeMode port. `eval` is on by default like Native (`omo-native-eval-enabled: false` turns it off); the codemode runtime runs in a `node:worker_threads` Worker so its first load does not block the host. `v2/tools/native-eval.ts` registers `eval` (`codemode: false`, permission action `eval`) and refuses child sessions and the read-only roles (the V2 agents that deny `bash`); a `context` hook hides it from them and swaps in codemode's own description and schema once loaded. `v2/tools/codemode-loader.ts` imports the installed `@code-yeongyu/senpi-codemode` 2026.11.5-1 lazily through computed file URLs (version-pinned, load timeout, model-visible error); the package is now a root runtime dependency and a V2 build external, because bundling it breaks its worker and prelude asset resolution. `v2/tools/codemode-session.ts` keeps one kernel manager, handle registry and detached-cell manager per session, with plugin-built Native default settings (never `~/.senpi/agent/codemode.json`), serialized calls, bounded start and dispose, and teardown on session deletion, plugin dispose and process `exit`/`beforeExit`. `v2/tools/codemode-host-tools.ts` routes a cell's `tools.X` calls only to plugin-owned tools and passes the live kernel-tools capability from codemode's own senpi copy explicitly, for S9d. Real-host spike QA showed the first main-thread import froze the whole OpenCode server for 15-30 s (opencode.exe's runtime Bun plugin scans every main-thread import synchronously), so the loader, the session registry (now `codemode-session-registry.ts`) and the description builder run in a Bun Worker (`codemode-worker.ts` entry, `codemode-worker-runtime.ts`); the main thread keeps a message client (`codemode-worker-client.ts` over `codemode-rpc.ts`, contract in `codemode-worker-protocol.ts`) that spawns the worker lazily, sends abort as a message, runs owned host tools for cells, releases on session deletion, disposes then terminates on plugin dispose, replaces a dead worker on the next call, and at process `exit` terminates it and kills the subprocess-kernel pids it reported (`codemode-kernel-reaper.ts`: `taskkill /T /F` on Windows, process group then pid on POSIX). The live kernel-tools capability stays in the worker; owned tools get a message-backed proxy with its `capabilities`/`describe`/`invoke` (scope, signal, invoker) surface (`codemode-capability.ts`) for S9d. `script/build-nodes.ts` emits the worker entry as `codemode-worker.js` next to both bundles' chunks (`dist/` and `dist/v2/`, since the root bundle carries the V2 graph lazily), and the client finds it by that name next to its own chunk, with a model-visible error if it is missing.
