### Fixed

- On Windows, a reflection run whose child finished successfully no longer ends with its supervisor exiting 1 and no `outcome.json`. When the supervisor hands its concurrency slot to the child, the slot record now keeps the supervisor as a second owner, so the next queued run treats the slot as abandoned only when both the child and the supervisor have exited. Before, the queued run could delete the slot lock the moment the child exited, while the supervisor was deleting it too, and Windows answered the supervisor's delete with EPERM. The supervisor's exit handler also stops reading the slot after it was released, and `/doctor` no longer reports a handed-over slot as stale while its supervisor still runs. This also made the Windows `supervisor-slot` FIFO test fail intermittently.
